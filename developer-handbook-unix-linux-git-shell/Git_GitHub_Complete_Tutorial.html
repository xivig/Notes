CHAPTER 01 / ARCHITECTURAL FOUNDATIONS

Git and GitHub: know the difference

Understand the distinct separation between Git (the local distributed version control engine) and GitHub (the cloud-hosted collaboration platform), and master Git's internal object model.

Many beginners conflate Git with GitHub, leading to confusion about where code lives and when synchronization happens. Git is an offline tool running locally on your computer; GitHub is an online service that hosts Git repositories in the cloud.

DimensionGit (Command-Line Tool)GitHub (Cloud Platform)
What it isDistributed version control system (CLI tool)Cloud-based hosting and collaboration web service
Where it runsLocally on your laptop or serverRemote cloud infrastructure operated by GitHub/Microsoft
Network requirement100% offline: record commits, create branches, view history without internetRequires active internet to push, pull, review PRs, or trigger CI/CD
Primary functionsgit add, commit, branch, diff, log, rebasePull Requests, Issue tracking, Code Reviews, Actions, Discussions
Created byLinus Torvalds (2005) for Linux kernel developmentChris Wanstrath, P.J. Hyett, Tom Preston-Werner (2008)
AlternativesMercurial, Subversion (SVN), JujutsuGitLab, Bitbucket, Gitea, Sourcehut

Git's Internal Object Architecture

Unlike legacy version control systems (like SVN or CVS) that record file diffs, Git stores data as a sequence of complete cryptographic snapshots. Git uses 4 fundamental object types stored inside the .git/objects/ directory, keyed by 40-character SHA-1 (or SHA-256) hashes:

Object TypeRoleInternal Representation
Blob (Binary Large Object)Stores file contents onlyPure data without filename, timestamps, or permissions
TreeRepresents a directoryList of pointers to blobs and other sub-trees with filenames and mode bits
CommitPermanent snapshot of project statePointer to a top-level Tree, parent commit SHA(s), author, committer, timestamp, message
Annotated TagPermanent reference markPointer to a specific commit with message, tagger info, and optional GPG signature
The Content-Addressable Database: Because Git calculates the hash of every object based strictly on its content, you cannot alter a single character in a file or commit message without changing every subsequent hash. This gives Git its mathematical tamper-resistance. 
# Inspect Git's plumbing objects directly:
# 1. View the commit object at HEAD
git cat-file -p HEAD

# 2. View the root Tree pointed to by the commit
git cat-file -p HEAD^{tree}

# 3. View the raw content of a file blob
git cat-file -p

Initialize version control in a project directory, explore the anatomy of the hidden .git metadata folder, and understand repository scoping.

A Git repository is simply a directory on your filesystem that contains a hidden .git folder. This folder acts as the repository database, tracking every snapshot, reference, and config setting.

# 1. Create a fresh project directory and enter it

# 2. Initialize Git tracking

CHAPTER 04 / THE CORE WORKFLOW

The everyday Git workflow

Master the Three Trees of Git: the Working Directory, the Staging Area (Index), and the Commit History. Write atomic commits following professional conventions.

To use Git with total confidence, you must build a clear mental model of Git's Three Trees architecture:

State / AreaLocationCommand to Move ForwardCommand to Roll Back
1. Working DirectoryFiles visible in your code editorgit add <file> → stages changesgit restore <file> → discards edits
2. Staging Area (Index).git/index (draft for next snapshot)git commit -m "..." → commits snapshotgit restore --staged <file> → un-stages
3. Commit History (HEAD)Permanent immutable database in .git/git push → publishes to remotegit revert <hash> → creates undo commit

The 4-Step Everyday Loop

# Step 1: Check status to see what has changed
git status -s  # Short format (?? untracked, M modified, A staged)

# Step 2: Review exact code diffs before staging
git diff       # Inspect un-staged line changes

# Step 3: Stage specific files (or patches) for the commit
git add README.md src/app.js
# Or stage interactively: git add -p (review hunk by hunk)

# Step 4: Verify staged snapshot
git diff --staged  # Inspect what will actually go into the commit

# Step 5: Record atomic commit with a clear message
git commit -m "feat(auth): add login endpoint with JWT validation"

Conventional Commit Messages Architecture

Standardized Commit Format: Teams follow the Conventional Commits specification: <type>(<optional-scope>): <imperative-summary>
  • feat: A new user-facing feature or API endpoint
  • fix: A bug fix for user or developer
  • docs: Documentation only changes
  • refactor: Code changes that neither fix bugs nor add features
  • test: Adding or correcting automated tests
  • chore: Build tasks, dependency updates, package config

CHAPTER 05 / CLOUD SYNCHRONIZATION

Publish the project on GitHub

Connect local repositories to GitHub using HTTPS with Personal Access Tokens (PAT) or modern ED25519 SSH keys, configure origin remotes, and push upstream.

Once you have local commits, you can publish them to GitHub for backup, sharing, and team collaboration. GitHub authentication requires either Personal Access Tokens (PAT) or SSH Keys (passwords were deprecated in 2021).

Authentication: SSH vs. HTTPS (PAT)

ProtocolURL FormatAuthentication MethodRecommendation
SSHgit@github.com:user/repo.gitPublic/Private cryptographic key pairBest for developers: Zero password prompts after setup
HTTPShttps://github.com/user/repo.gitGitHub Personal Access Token (PAT)Good for firewalled networks blocking port 22

Step-by-Step SSH Setup (Modern ED25519)

# 1. Generate an ED25519 key pair (modern, faster, and more secure than RSA)
ssh-keygen -t ed25519 -C "your.email@example.com"
# Press Enter to accept default location (~/.ssh/id_ed25519)

# 2. Start the ssh-agent and add your private key
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# 3. Copy the public key to clipboard
# macOS:   pbcopy < ~/.ssh/id_ed25519.pub
# Linux:   cat ~/.ssh/id_ed25519.pub
# Windows: clip < ~/.ssh/id_ed25519.pub

# 4. In GitHub: Settings -> SSH and GPG keys -> New SSH Key -> Paste and Save

# 5. Test connection
ssh -T git@github.com
# Expected: "Hi username! You've successfully authenticated..."

Linking Local Repo & First Push

# Link local repo to remote with the standard name 'origin'
git remote add origin git@github.com:username/my-awesome-app.git

# Verify remote configuration
git remote -v

# Push local 'main' branch to remote 'origin' and set upstream tracking (-u)
git push -u origin main
The -u (Upstream) Flag: Running git push -u origin main sets up tracking relationship between local main and origin/main. For all future pushes and pulls on this branch, you simply type git push or git pull!

CHAPTER 07 / PARALLEL DEVELOPMENT

Branches: work safely without disturbing main

Create lightweight branches, master the modern switch/restore CLI commands, explore team branching strategies (GitHub Flow vs Git Flow), and manage branch lifecycles.

In Git, a branch is not a heavy copy of your codebase. It is merely a 41-byte plaintext file inside .git/refs/heads/ containing the 40-character commit hash of the branch tip. Creating, switching, and deleting branches happens instantaneously.

Modern git switch vs. Legacy git checkout

Why Git Introduced switch & restore in v2.23: Historically, git checkout was overloaded with two completely unrelated duties: switching branches AND discarding uncommitted file edits. Git introduced git switch (strictly for branches) and git restore (strictly for files) to eliminate dangerous accidental data loss. 
# Modern command (Recommended):
git switch -c feature/payment-gateway  # Create and switch to new branch
git switch main                        # Switch back to main

# Legacy command:
git checkout -b feature/payment-gateway
git checkout main

Branching Models Comparison

Branching StrategyPrimary BranchesWorkflow StyleBest Suited For
GitHub Flowmain, short-lived feature/* branchesBranches deploy to production immediately upon PR mergeWeb applications, SaaS, microservices, agile teams
Trunk-Based Developmentmain (trunk), feature flagsDevelopers commit directly or via micro-PRs merged multiple times dailyHigh-velocity continuous delivery engineering orgs
Git Flowmain, develop, release/*, hotfix/*Scheduled releases with strict staging cyclesPackaged software, mobile apps with app-store review gates
 
# Inspect all local and remote tracking branches
git branch -a -v

# Safely delete a branch that has already been merged
git branch -d feature/payment-gateway

# Force-delete a branch containing unmerged experimental commits
git branch -D feature/abandoned-experiment

# Rename current branch locally
git branch -m feature/new-branch-name

CHAPTER 08 / REPOSITORY SYNCHRONIZATION

Keep your local and GitHub copies in sync

Dissect the critical difference between git fetch and git pull, understand fast-forward vs 3-way merge commits, and resolve diverged branch states.

In distributed version control, your local repository and the GitHub remote evolve independently. Understanding how Git synchronizes these separate graphs prevents unwanted merge commits and broken histories.

git fetch vs. git pull: The Crucial Difference

CommandWhat It DoesWorking Files Affected?Safety Profile
git fetchDownloads new commits and branch refs from remote into origin/* tracking branchesNo (zero changes to your editor or working files)100% Safe: Lets you inspect incoming changes before merging
git pullRuns git fetch followed immediately by git merge origin/<branch>Yes: Modifies working files and creates commits or merge conflictsCan trigger unexpected merge commits if branches diverged
The Professional Sync Habit: Run git fetch origin, then inspect what teammates pushed with git log HEAD..origin/main --oneline. If the diff looks good, merge with git merge origin/main.

Fast-Forward vs. Three-Way Merge

Merge TypeConditionGit Action
Fast-Forward (ff)Your local branch has no new commits since you branched from originGit simply advances your branch pointer forward to match remote. No new commit object is created.
Three-Way MergeBoth you and the remote created commits since divergingGit computes common ancestor and generates a special Merge Commit with two parent hashes.
 
# Safe pull that guarantees no surprise merge commits:
git pull --ff-only

# Alternative: Rebase your local commits on top of incoming remote commits
git pull --rebase origin main

CHAPTER 09 / TEAM COLLABORATION

Pull requests: the collaboration workflow

Master the end-to-end Pull Request (PR) lifecycle: feature branching, pushing upstream, creating PRs, code reviews, draft PRs, and PR merge strategies.

A Pull Request (PR) is a GitHub feature that allows developers to propose changes from a feature branch into a target branch (typically main). It serves as the central hub for code review, automated testing (CI/CD), security scanning, and architectural discussion.

The 6-Stage PR Lifecycle

  1. Branch: Create a dedicated branch off latest main: git switch -c feature/dark-mode.
  2. Develop & Commit: Build your feature with focused, atomic commits.
  3. Push: Publish your branch upstream: git push -u origin feature/dark-mode.
  4. Open PR: Navigate to GitHub and click Compare & pull request. Fill out description and link issue numbers (e.g. Fixes #142).
  5. Code Review & CI: Automated tests run via GitHub Actions. Teammates review line-by-line diffs and request changes.
  6. Merge & Delete: Once approved and green, merge into main and delete the remote branch.

GitHub PR Merge Strategies Comparison

Merge StrategyCommit Graph OutcomeWhen to Use
Create a Merge CommitPreserves every individual commit plus a merge commit (two parents)Open-source projects where every granular commit signature matters
Squash and MergeCondenses all branch commits into a single clean commit on mainIndustry standard for feature teams: Keeps main history clean and easy to revert
Rebase and MergeReplays all branch commits 1-by-1 linearly onto main without merge commitTeams wanting a strict linear history without extra merge nodes
Draft Pull Requests: Open a PR as a "Draft" when your work is in progress. This signals to teammates that the code is not ready for formal review yet, while allowing you to preview CI test runs and gather early feedback.

CHAPTER 10 / DISASTER RECOVERY & UNDO

Undo carefully: the commands worth knowing

A comprehensive decision framework for undoing mistakes across the Working Tree, Staging Area, and Commit History using restore, reset, revert, and clean.

One of Git's greatest strengths is that almost nothing is truly lost once committed. Choosing the correct undo command depends on which of the Three Trees contains the unwanted change.

The Complete Undo Decision Matrix

ScenarioTarget StateRecommended CommandData Loss Risk?
Discard unstaged edits in a fileWorking Treegit restore <file>Permanent: Overwrites uncommitted edits with last commit
Discard ALL unstaged edits in projectWorking Treegit restore .Permanent: Wipes all local unstaged work
Unstage a file (keep local edits)Staging Areagit restore --staged <file>Safe: File remains modified in working tree
Undo last commit (keep files staged)Commit Historygit reset --soft HEAD~1Safe: Commits undone; edits stay staged
Undo last commit (keep files unstaged)Commit Historygit reset --mixed HEAD~1Safe: Commits undone; edits stay in working tree
Destroy last commit and wipe filesAll Treesgit reset --hard HEAD~1Dangerous: Destroys commit and uncommitted edits!
Safely undo a public commit pushed to GitHubRemote Historygit revert <commit_hash>100% Safe: Creates a NEW commit reversing the changes
Remove untracked files and foldersWorking Treegit clean -fdPermanent: Deletes untracked files not in .gitignore
The Golden Rule of git reset: NEVER run git reset --hard on commits that have already been pushed to a shared remote branch (like main). Rewriting shared public history forces merge nightmares on your entire team. Use git revert instead! 
# Example: Safely undoing a pushed faulty commit (revert)
# 1. Locate the bad commit hash in history
git log --oneline -n 5

# 2. Revert the commit (creates a new commit that inverts the patch)
git revert a1b2c3d -m "Revert faulty billing migration"

# 3. Push the safe reversal commit upstream
git push origin main

CHAPTER 11 / CONFLICT RESOLUTION

Resolve a merge conflict

Understand why conflicts occur, dissect the anatomy of conflict markers, resolve overlapping line edits, configure graphical merge tools, and abort safely.

A merge conflict occurs when two branches modify the exact same lines in a file differently, or when one branch deletes a file that another branch modified. Git cannot guess developer intent, so it pauses the merge and asks you to make the decision.

Anatomy of Conflict Markers

<<<<<<< HEAD (Current branch: main)
const API_URL = "https://api.production.internal/v2";
=======
const API_URL = "https://api.v2.global-gateway.com";
>>>>>>> feature/gateway-migration (Incoming branch)
  • <<<<<<< HEAD: The state of the code on your currently checked-out branch.
  • =======: The divider separating conflicting changes.
  • >>>>>>> branch-name: The state of the code on the incoming branch you are merging.

Step-by-Step Resolution Workflow

# 1. Identify conflicted files (marked as 'both modified')
git status

# 2. Open conflicted files in VS Code / Vim / editor
# Choose: Keep Current, Keep Incoming, or Write a Hybrid of both.
# DELETE all marker lines (<<<<<<<, =======, >>>>>>>)!

# 3. Mark the conflict resolved by staging the file
git add src/config.js

# 4. Finalize the merge commit
git commit -m "merge: resolve API_URL conflict between main and feature/gateway-migration"

# If you get into trouble and want to cancel the merge cleanly:
git merge --abort  # Restores working tree to state before merge began!
Fast-Resolution Shortcuts: If you know you want to accept your current branch's version completely: git checkout --ours <file>.
If you want to accept the incoming branch's version completely: git checkout --theirs <file>.

CHAPTER 14 / ERROR DIAGNOSTICS

Troubleshooting: 12 common beginner errors

Step-by-step diagnostic solutions for the most frequent, frustrating Git errors encountered by developers and teams.

1. "fatal: not a git repository"

Cause: You ran a Git command in a folder that has not been initialized with Git or is outside the repository boundary.

# Solution: Navigate into your project folder or initialize it
cd path/to/actual/project
git status
# Or if this is a brand new project: git init

2. "error: failed to push some refs to '...'" (Non-Fast-Forward)

Cause: GitHub contains commits that you do not have locally (e.g. someone else pushed, or you created README on GitHub).

# Solution: Fetch and merge remote changes before pushing
git pull --rebase origin main
git push origin main

3. "fatal: refusing to merge unrelated histories"

Cause: You initialized a local repo and created a GitHub repo with a README independently; they share no common root commit.

# Solution: Allow Git to merge independent commit roots
git pull origin main --allow-unrelated-histories

4. "remote: error: GH001: Large files detected (>100MB)"

Cause: GitHub blocks commits containing individual files larger than 100MB.

# Solution: Unstage the large file and track with Git LFS (Large File Storage)
git rm --cached path/to/large_file.zip
git commit --amend -CHEAD
git lfs install
git lfs track "*.zip"
git add .gitattributes
git commit -m "chore: track large archive via Git LFS"

5. "warning: LF will be replaced by CRLF"

Cause: Normal notification on Windows when Git converts line endings.

# Solution: Configure autocrlf properly
git config --global core.autocrlf true   # On Windows
git config --global core.autocrlf input  # On macOS/Linux

6. "You are in 'detached HEAD' state"

Cause: You checked out a specific commit hash or tag rather than a named branch. Any new commits made here will not belong to any branch.

# Solution: Create a new branch pointing to this state to save work
git switch -c rescue-branch
# Or return safely to main: git switch main

CHAPTER 16 / DAILY BEST PRACTICES

A safe daily workflow

An 8-step battle-tested daily operating procedure for developers working on agile software teams to avoid merge headaches and lost code.

Adopting a disciplined daily routine eliminates 95% of merge conflicts, broken builds, and lost work in team repositories.

The 8-Step Daily Engineering Cycle

  1. Start of Day Sync: Switch to main and pull the latest upstream changes: 
    git switch main && git pull --ff-only
  2. Branch Off Fresh Base: Never start work on an old branch. Always branch off the freshly updated main: 
    git switch -c feat/user-onboarding
  3. Make Small, Focused Commits: Commit logical units of work frequently rather than one massive commit at the end of the week: 
    git commit -m "feat(ui): add signup modal skeleton"
  4. Run Tests Locally Before Staging: Verify automated tests pass locally before committing: 
    npm test || pytest || cargo test
  5. Inspect Staged Diff Before Finalizing: Always check what you are about to seal into history: 
    git diff --staged
  6. Rebase on Main Before Opening PR: Keep your branch up to date with teammates' merged work: 
    git fetch origin main && git rebase origin/main
  7. Push and Open PR: Push upstream with tracking and open a Pull Request: 
    git push -u origin feat/user-onboarding
  8. Delete Merged Branches: Once the PR is merged on GitHub, delete the local branch to keep your environment clean: 
    git switch main && git pull && git branch -d feat/user-onboarding

CHAPTER 19 / PUSH REJECTIONS & DIVERGENCE

Push rejected: understand and fix it correctly

Demystify [rejected - non-fast-forward] errors, understand commit graph divergence, avoid the hazards of force push, and use safe --force-with-lease.

When you run git push and Git rejects your command with [rejected - non-fast-forward], it is not broken. Git is actively preventing you from destroying commits that exist on GitHub but not on your local machine.

Why Non-Fast-Forward Happens

Remote (origin/main):  A --- B --- C --- D (Teammate pushed D)
Local (main):          A --- B --- C --- E (You committed E locally)

Both commits D and E share common parent C, but neither is an ancestor of the other. If Git allowed you to push E directly, commit D would be erased from the remote branch!

The Two Correct Solutions

Solution StrategyCommandOutcome
Method A: Pull Rebase (Preferred)git pull --rebase origin mainReplays your local commit E on top of D, producing a clean linear history: A-B-C-D-E'.
Method B: Pull Mergegit pull origin mainCreates a merge commit tying together D and E. Leaves history intact but adds merge noise.
The Danger of git push --force: Running git push -f forces the remote branch to match your local state, permanently destroying any commits pushed by colleagues. If you must update a rebased feature branch, ALWAYS use the safe alternative: git push --force-with-lease (Refuses to push if someone else pushed changes you haven't seen!).

CHAPTER 22 / ADVANCED DISASTER LABS

Git mastery lab: practice the difficult cases

Hands-on disaster recovery simulations: recover accidentally deleted branches with git reflog, cherry-pick hotfixes across branches, and bisect regression bugs.

These advanced lab exercises simulate high-stakes production scenarios. Complete them in a disposable repository to build true mastery.

Lab 1: Recover a Deleted Branch Using git reflog

The Safety Net of git reflog: The reflog (Reference Log) records every movement of HEAD on your machine for 90 days. Even if you run git branch -D or reset hard, the commits still exist in reflog! 
# Scenario: You accidentally force-deleted a feature branch with 3 days of work!
git branch -D feature/important-work

# 1. View the local reference log:
git reflog
# Output:
# a1b2c3d HEAD@{0}: checkout: moving from feature/important-work to main
# 9f8e7d6 HEAD@{1}: commit: feat: complete database schema migration

# 2. Resurrect the branch at the exact commit hash from reflog:
git branch feature/important-work 9f8e7d6

# Result: Branch and all commits are 100% recovered!

Lab 2: Cherry-Pick a Specific Hotfix Commit

When a bug fix was committed to an unready experimental feature branch, but you need to deploy only that fix into production immediately:

# 1. Find the commit hash of the bug fix on the feature branch
git log feature/experimental-redesign --oneline

# 2. Switch to production branch
git switch main

# 3. Cherry-pick only that specific commit
git cherry-pick 4c5d6e7

# Git applies the exact patch from that commit onto main with a new commit hash!

Lab 3: Binary Search for Bugs with git bisect

When a bug was introduced somewhere among the last 200 commits, git bisect performs an automated binary search (O(log N)) to pinpoint the exact commit that introduced the breakage in seconds:

# 1. Start bisect mode
git bisect start

# 2. Mark current state as broken
git bisect bad

# 3. Mark a known good historical version
git bisect good v1.2.0

# 4. Git automatically checks out middle commit. Run your test:
npm test
# If test passes: git bisect good
# If test fails:  git bisect bad

# 5. After log2(N) checks, Git announces the culprit commit!
# Exit bisect mode when done:
git bisect reset
