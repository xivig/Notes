01. ORM Architectures, Impedance Mismatch & Setup

An Object-Relational Mapper (ORM) bridges object-oriented domain models in memory with relational tables stored on disk. Choosing between Active Record (Laravel Eloquent) and Data Mapper (Symfony Doctrine ORM 3) shapes your domain boundaries, testability, performance profile, and migration strategy for years.

1. The Object-Relational Impedance Mismatch

Relational databases think in sets, normalized tables, foreign keys, and scalar types, whereas OOP applications think in object graphs, behavior, inheritance, and reference identity (===):

// ============================================================================
// PART A: Mini ActiveRecord (Row + Persistence live inside Model class)
// ============================================================================
abstract class ActiveRecordModel
{
    public static ?PDO $db = null;
    public ?int $id = null;

    protected static function table(): string
    {
        return strtolower((new ReflectionClass(static::class))->getShortName()) . 's';
    }
}

final class ActiveProduct extends ActiveRecordModel
{
    public function __construct(
        public string $sku,
        public string $name,
        public int $price_cents,
    ) {}

    public function save(): void
    {
        if ($this->id === null) {
            $stmt = self::$db->prepare('INSERT INTO products (sku, name, price_cents) VALUES (?, ?, ?)');
            $stmt->execute([$this->sku, $this->name, $this->price_cents]);
            $this->id = (int) self::$db->lastInsertId();
            return;
        }
        $stmt = self::$db->prepare('UPDATE products SET name = ?, price_cents = ? WHERE id = ?');
        $stmt->execute([$this->name, $this->price_cents, $this->id]);
    }

    public static function find(int $id): ?self
    {
        $stmt = self::$db->prepare('SELECT * FROM products WHERE id = ?');
        $stmt->execute([$id]);
        $row = $stmt->fetch();
        if (! $row) {
            return null;
        }
        $m = new self($row['sku'], $row['name'], (int) $row['price_cents']);
        $m->id = (int) $row['id'];
        return $m;
    }
}

// ============================================================================
// PART B: Mini DataMapper + Unit of Work + Identity Map (Domain decoupled from SQL)
// ============================================================================
final class DomainProduct
{
    private ?int $id = null;

    public function __construct(
        private string $sku,
        private string $name,
        private int $priceCents,
    ) {
        if ($priceCents < 0) {
            throw new InvalidArgumentException('Price cannot be negative.');
        }
    }

    public function id(): ?int { return $this->id; }
    public function sku(): string { return $this->sku; }
    public function name(): string { return $this->name; }
    public function priceCents(): int { return $this->priceCents; }

    public function applyDiscount(int $percent): void
    {
        $this->priceCents = (int) round($this->priceCents * (100 - $percent) / 100);
    }

    /** @internal Hydrated by EntityManager only */
    public function bindDatabaseId(int $id): void { $this->id = $id; }
}

final class MiniEntityManager
{
    /** @var array<int, DomainProduct> */
    private array $identityMap = [];
    /** @var array<int, DomainProduct> */
    private array $newQueue = [];
    /** @var array<int, array{sku: string, name: string, priceCents: int}> */
    private array $originalSnapshot = [];

    public int $flushQueries = 0;

    public function __construct(private readonly PDO $pdo) {}

    public function persist(DomainProduct $entity): void
    {
        if ($entity->id() === null) {
            $this->newQueue[spl_object_id($entity)] = $entity;
        }
    }

    public function find(int $id): ?DomainProduct
    {
        if (isset($this->identityMap[$id])) {
            return $this->identityMap[$id]; // Identity Map hit: zero SQL query!
        }

        $stmt = $this->pdo->prepare('SELECT * FROM products WHERE id = ?');
        $stmt->execute([$id]);
        $row = $stmt->fetch();
        if (! $row) {
            return null;
        }

        $entity = new DomainProduct($row['sku'], $row['name'], (int) $row['price_cents']);
        $entity->bindDatabaseId((int) $row['id']);
        $this->identityMap[(int) $row['id']] = $entity;
        $this->originalSnapshot[(int) $row['id']] = [
            'sku' => $entity->sku(),
            'name' => $entity->name(),
            'priceCents' => $entity->priceCents(),
        ];

        return $entity;
    }

    public function flush(): void
    {
        $this->pdo->beginTransaction();
        try {
            // 1. Insert queued new entities
            foreach ($this->newQueue as $entity) {
                $stmt = $this->pdo->prepare('INSERT INTO products (sku, name, price_cents) VALUES (?, ?, ?)');
                $stmt->execute([$entity->sku(), $entity->name(), $entity->priceCents()]);
                $newId = (int) $this->pdo->lastInsertId();
                $entity->bindDatabaseId($newId);
                $this->identityMap[$newId] = $entity;
                $this->originalSnapshot[$newId] = [
                    'sku' => $entity->sku(),
                    'name' => $entity->name(),
                    'priceCents' => $entity->priceCents(),
                ];
                $this->flushQueries++;
            }
            $this->newQueue = [];

            // 2. Dirty-checking: only UPDATE entities whose snapshot changed!
            foreach ($this->identityMap as $id => $entity) {
                $orig = $this->originalSnapshot[$id];
                if ($orig['name'] !== $entity->name() || $orig['priceCents'] !== $entity->priceCents()) {
                    $stmt = $this->pdo->prepare('UPDATE products SET name = ?, price_cents = ? WHERE id = ?');
                    $stmt->execute([$entity->name(), $entity->priceCents(), $id]);
                    $this->originalSnapshot[$id]['name'] = $entity->name();
                    $this->originalSnapshot[$id]['priceCents'] = $entity->priceCents();
                    $this->flushQueries++;
                }
            }

            $this->pdo->commit();
        } catch (Throwable $e) {
            $this->pdo->rollBack();
            throw $e;
        }
    }
}

$em = new MiniEntityManager($pdo);
$dm = new DomainProduct('SKU-200', 'USB-C Dock', 8000);
$em->persist($dm);
$em->flush(); // Executes 1 batched INSERT

$dmA = $em->find($dm->id());
$dmB = $em->find($dm->id());
assert($dmA === $dmB, 'DataMapper Identity Map guarantees single object identity === per PK.');

$dmA->applyDiscount(25); // Changes price in RAM from 8000 -> 6000 without SQL yet!
$em->flush();            // Dirty-checker detects price change and issues 1 UPDATE!

assert($dmB->priceCents() === 6000, 'Identity Map reflects updated state identically across references.');
echo "[DataMapper] Identity === preserved? true | Final price after 25% discount: {$dmB->priceCents()} cents | Flush SQL writes: {$em->flushQueries}\n";

02. Defining Models, Entities & Value Objects

How you map database columns to PHP types determines type safety, domain clarity, and defense against invalid states. This chapter compares Laravel 12/13 Models + Casts + PHP Attributes side by side with Doctrine ORM 3 PHP 8 Attributes + Embeddable Value Objects.

1. Laravel Eloquent Model (App\Models\Product)

In Laravel, database columns live in migrations (database/migrations/), while runtime coercion, mutability rules, and visibility live cleanly in the Model:

PHP
<?php

declare(strict_types=1);

namespace App\Models;

use App\Enums\ProductStatus;
use Illuminate\Database\Eloquent\Attributes\Fillable;
use Illuminate\Database\Eloquent\Attributes\Hidden;
use Illuminate\Database\Eloquent\Attributes\Table;
use Illuminate\Database\Eloquent\Concerns\HasUuids;
use Illuminate\Database\Eloquent\Factories\HasFactory;
use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\SoftDeletes;

// Laravel 13 PHP Attributes work alongside classic $fillable / $hidden properties
#[Table(name: 'products')]
#[Fillable(['sku', 'name', 'price_cents', 'status', 'metadata', 'published_at'])]
#[Hidden(['internal_cost_cents'])]
final class Product extends Model
{
    use HasFactory, HasUuids, SoftDeletes;

    /** Tell HasUuids which secondary column uses UUID if id remains BIGINT: */
    public function uniqueIds(): array
    {
        return ['public_uuid'];
    }

    /** PHP 8 Backed Enum, JSON, immutable datetime & boolean casting: */
    protected function casts(): array
    {
        return [
            'price_cents' => 'integer',
            'status' => ProductStatus::class,
            'metadata' => 'array',
            'published_at' => 'immutable_datetime',
        ];
    }
}

2. Doctrine ORM 3 Entity + Value Objects (#[ORM\Entity])

Doctrine makes the PHP Entity the single source of truth for schema structure (doctrine:migrations:diff generates SQL migrations by diffing your PHP attributes against the DB):

PHP
<?php

declare(strict_types=1);

namespace App\Entity;

use App\Enum\ProductStatus;
use App\Repository\ProductRepository;
use Doctrine\DBAL\Types\Types;
use Doctrine\ORM\Mapping as ORM;

#[ORM\Embeddable]
final readonly class Money
{
    public function __construct(
        #[ORM\Column(type: Types::INTEGER)]
        public int $amountCents,
        #[ORM\Column(length: 3)]
        public string $currency = 'USD',
    ) {
        if ($amountCents < 0) {
            throw new \InvalidArgumentException('Money amount cannot be negative.');
        }
    }
}

#[ORM\Entity(repositoryClass: ProductRepository::class)]
#[ORM\Table(name: 'products')]
#[ORM\Index(name: 'idx_products_status_created', columns: ['status', 'created_at'])]
#[ORM\UniqueConstraint(name: 'uniq_products_sku', columns: ['sku'])]
final class Product
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    #[ORM\Column(type: Types::BIGINT)]
    private ?int $id = null;

    #[ORM\Embedded(class: Money::class, columnPrefix: 'price_')]
    private Money $price; // Persists as price_amount_cents + price_currency!

    #[ORM\Column(length: 20, enumType: ProductStatus::class)]
    private ProductStatus $status = ProductStatus::Draft;

    #[ORM\Column(type: Types::DATETIME_IMMUTABLE)]
    private \DateTimeImmutable $createdAt;

    public function __construct(
        #[ORM\Column(length: 40)]
        private string $sku,
        #[ORM\Column(length: 180)]
        private string $name,
        Money $price,
    ) {
        $this->price = $price;
        $this->createdAt = new \DateTimeImmutable();
    }

    public function id(): ?int { return $this->id; }
    public function price(): Money { return $this->price; }
}

4. Custom Value Object Cast in Eloquent (CastsAttributes)

Keep Money type safety in Eloquent too by binding custom casts:

PHP
use Illuminate\Contracts\Database\Eloquent\CastsAttributes;
use Illuminate\Database\Eloquent\Model;

final class MoneyCast implements CastsAttributes
{
    public function get(Model $model, string $key, mixed $value, array $attributes): Money
    {
        return new Money((int) $value, (string) ($attributes['currency'] ?? 'USD'));
    }

    public function set(Model $model, string $key, mixed $value, array $attributes): array
    {
        if (! $value instanceof Money) {
            throw new \InvalidArgumentException('Expected Money instance.');
        }

        return ['price_cents' => $value->amountCents, 'currency' => $value->currency];
    }
}

Key Takeaways

  • Avoid FLOAT/DOUBLE for financial amounts in both ORMs — store integer minor units (amount_cents) or DECIMAL(12,2) backed by a typed Value Object (Money).
  • Prefer immutable_datetime / \DateTimeImmutable over mutable Carbon/\DateTime so passing timestamps around never mutates entity properties by accident.

03. Persisting, Updating, Upserts & Entity States

Persisting data looks simple ($model->save() vs $em->flush()), yet subtle differences between immediate Active Record queries and Doctrine Unit of Work change-tracking catch developers off guard.

1. Create, Update & Delete Side-by-Side

Laravel Eloquent (Immediate SQL Execution)

PHP
// 1. Instance + save() (useful when setting computed fields explicitly)
$product = new Product();
$product->sku = 'KB-900';
$product->name = 'Keychron K2';
$product->price_cents = 9900;
$product->save(); // Fires INSERT immediately

// 2. Mass-assignment via validated FormRequest data ONLY
$product = Product::create($request->validated());

// 3. Atomic find-or-create / upsert helpers
$tag = Tag::firstOrCreate(
    ['slug' => 'mechanical-keyboards'],   // Lookup WHERE criteria
    ['name' => 'Mechanical Keyboards'],   // Additional INSERT columns if missing
);

Product::updateOrCreate(
    ['sku' => 'KB-900'],
    ['price_cents' => 8900],
);

// 4. Delete (soft delete if SoftDeletes trait is active; otherwise DELETE)
$product->delete();
$product->forceDelete(); // Permanent SQL DELETE

Symfony Doctrine ORM 3 (Deferred Unit of Work)

PHP
// 1. Creating a new Entity: New -> Managed -> INSERT on flush()
$product = new Product('KB-900', 'Keychron K2', new Money(9900));
$em->persist($product); // No SQL ran yet! UnitOfWork only tracks $product in memory
$em->flush();           // Opens DB transaction -> executes batched INSERTs -> commits!

// 2. Updating a Managed Entity: dirty-checking is AUTOMATIC (no persist() needed!)
$managed = $em->find(Product::class, $id);
$managed->rename('Keychron K2 Pro');
$em->flush(); // UnitOfWork diffs original snapshot vs current property -> fires UPDATE only if changed

// 3. Assigning a Foreign Key WITHOUT an extra SELECT (`getReference` Proxy!)
$categoryRef = $em->getReference(Category::class, $categoryId); // Zero DB query!
$product->assignCategory($categoryRef);
$em->flush();

// 4. Removing
$em->remove($managed);
$em->flush();

  • Never call $em->persist($existingEntity) needlessly on managed entities — UnitOfWork already tracks changes on every entity fetched from a repository.
  • Mass batch pitfall: calling flush() inside a 10,000-row loop kills performance. Batch persist() every 200 items, then call $em->flush(); $em->clear(); to purge the Identity Map safely!

3. High-Speed Bulk upsert() & Chunked Inserts

When importing thousands of catalog SKUs, one INSERT/UPDATE per loop takes seconds; single-query bulk upserts take milliseconds:

PHP
// Laravel Eloquent native multi-row SQL UPSERT (`INSERT ... ON DUPLICATE KEY UPDATE` / `ON CONFLICT`)
Product::upsert(
    values: [
        ['sku' => 'SKU-01', 'name' => 'Mouse', 'price_cents' => 2500],
        ['sku' => 'SKU-02', 'name' => 'Mat', 'price_cents' => 1500],
    ],
    uniqueBy: ['sku'],          // Requires UNIQUE index on MySQL/PostgreSQL/SQLite!
    update: ['name', 'price_cents'],
);
Note: Product::upsert() and Product::where(...)->update([...]) run directly at SQL level — skipping Eloquent/Doctrine model lifecycle events, timestamps casts checks, and observers. Reserve them for bulk syncs/ETL and re-touch updated_at manually when needed.

4. Defending Mass Assignment ($fillable vs DTO Hydration)

  • Eloquent fires SQL immediately on save(); Doctrine accumulates changes in memory until a single transactional $em->flush().
  • Use $em->getReference(Category::class, $id) in Doctrine when attaching known foreign keys to skip redundant SELECT roundtrips.
  • Never pass unvalidated $request->all() into create() or update() — strictly combine $fillable + $request->validated().

    }

    public function findPublishedDeals(int $maxCents): array
    {
        return $this->createQueryBuilder('p')
            ->andWhere('p.status = :status')
            ->andWhere('p.price.amountCents <= :max')

            ->setParameter('max', $maxCents)

3. Eloquent Global Scopes vs Doctrine SQL Filters (Multi-Tenancy)

For row-level multi-tenancy (tenant_id = ?) or soft-delete filtering, attach an automatic SQL clause across every query:

  • Eloquent Global Scope: implement Illuminate\Database\Eloquent\Scope (apply(Builder $b, Model $m)), attach with #[ScopedBy([TenantScope::class])], and bypass selectively with ->withoutGlobalScope(TenantScope::class).
  • Doctrine SQL Filter (SQLFilter): extend Doctrine\ORM\Query\Filter\SQLFilter, enable dynamically via $em->getFilters()->enable('tenant')->setParameter('tenant_id', $tenantId) — injects AND t0.tenant_id = ? cleanly even into DQL joins!

4. Parameterized Raw SQL & DQL Injection Pitfalls

NEVER interpolate user variables directly inside SQL/DQL strings (WHERE name LIKE '%{$q}%'), column names, or sort directions!

PHP
// WRONG (SQL Injection / DQL Injection!):
$posts = DB::select("SELECT * FROM products WHERE category = '{$input}'");
$dql = $em->createQuery("SELECT p FROM App\Entity\Product p ORDER BY p.{$sort}");

// RIGHT (Bound parameters + Strict Column Allowlist):
$rows = DB::select('SELECT id, name FROM products WHERE category_id = ? AND status = ?', [$catId, 'active']);

$allowedColumns = ['price.amountCents' => 'p.price.amountCents', 'createdAt' => 'p.createdAt'];
$orderColumn = $allowedColumns[$requestSort] ?? 'p.createdAt';
$qb->orderBy($orderColumn, $dir === 'asc' ? 'ASC' : 'DESC');

(In Doctrine DBAL 4 without Entity hydration, $connection->executeQuery('SELECT ... WHERE id = :id', ['id' => $id])->fetchAllAssociative() executes parameterized SQL cleanly.)

Key Takeaways

  • Put reusable predicates into Eloquent Scopes (scopePublished / #[Scope]) or Doctrine Repository methods so query rules aren't duplicated across controllers.
  • Prefer exists() over count() > 0 when checking existence — SQL stops at the first matching index leaf.
  • Never interpolate dynamic strings into raw SQL, whereRaw(), or ORDER BY — always bind parameters and allowlist dynamic sort columns.

3. The N+1 Query Problem & How Both ORMs Eliminate It

Suppose a page displays 25 products and accesses $product->category->name inside a loop:

  • Naive Lazy Loop: 1 query for 25 products + 25 separate SELECT * FROM categories WHERE id = ? queries = 26 queries.
  • Eloquent Batched Eager Loading (with): executes SELECT * FROM products + SELECT id, name FROM categories WHERE id IN (1,2,3,4,5) = 2 queries total!
PHP
  // Specify column projections (`:id,name`) — `id` is REQUIRED for Eloquent to match keys!
  $products = Product::with(['category:id,name', 'tags:id,name'])->latest()->get();
  // Later on already-loaded models:
  $products->loadMissing('supplier:id,company_name');
  • Doctrine JOIN FETCH (DQL Single-Query Hydration):
PHP
  $products = $entityManager->createQuery(
      'SELECT p, c FROM App\Entity\Product p INNER JOIN p.category c'
  )->getResult(); // 1 SQL query total!
  • Cartesian Product & Pagination Trap in Doctrine: NEVER combine ->setMaxResults(20) with a to-many JOIN FETCH (Order JOIN FETCH OrderLines) directly! SQL LIMIT 20 cuts across joined lines instead of orders — wrap it with Doctrine's Paginator (new Paginator($query)) or use two-step eager fetching (batch/IN).
  • Extra-Lazy Collections in Doctrine: set fetch: 'EXTRA_LAZY' on large collections ($post->getComments()->count() or ->slice(0, 10)) so SQL runs SELECT COUNT(*) or LIMIT 10 instead of loading 50,000 objects into RAM!

  • In Doctrine, modify the owning side (ManyToOne), use JOIN FETCH for to-one relations, and wrap paginated to-many JOIN FETCH queries in Doctrine\ORM\Tools\Pagination\Paginator.
  • Always define Relation::enforceMorphMap() in Laravel so database *_type strings don't couple directly to PHP FQCN refactors.

07. ACID Transactions, Savepoints & Concurrency Locks

Real-world inventory deductions, financial transfers, and multi-table state changes fail corruptively under concurrent requests unless guarded by ACID transactions, post-commit side-effect deferrals, and optimistic or pessimistic row locks.

1. Wrapping Atomic Multi-Step Writes (ACID)

Laravel Eloquent (DB::transaction + Automatic Deadlock Retries)

PHP
use Illuminate\Support\Facades\DB;

DB::transaction(function () use ($buyerId, $sku, $amountCents): void {
    $wallet = Wallet::where('user_id', $buyerId)->lockForUpdate()->firstOrFail();

    if ($wallet->balance_cents < $amountCents) {
        throw new DomainException('Insufficient funds.');
    }

    $wallet->decrement('balance_cents', $amountCents);
    Order::create(['user_id' => $buyerId, 'sku' => $sku, 'total_cents' => $amountCents]);

    // Fires ONLY AFTER the outer DB transaction commits successfully!
    DB::afterCommit(fn () => DispatchOrderEmailJob::dispatch($buyerId, $sku));
}, attempts: 3); // Retries automatically on MySQL/Postgres deadlock!

Symfony Doctrine ORM 3 ($em->wrapInTransaction)

PHP
$entityManager->wrapInTransaction(function (EntityManagerInterface $em) use ($buyerId, $amountCents): void {
    // Acquire pessimistic row lock via LockMode!
    $wallet = $em->find(Wallet::class, $buyerId, \Doctrine\DBAL\LockMode::PESSIMISTIC_WRITE);
    $wallet->debit($amountCents);
    $em->persist(new LedgerEntry($wallet, -$amountCents));
    // wrapInTransaction automatically flushes & commits, or rolls back on exception!
});
Warning: Critical Doctrine Exception & Worker Pitfall
If a DBALException or uncaught exception happens during $em->flush() and rolls back manually in older beginTransaction() blocks, Doctrine closes the EntityManager (!$em->isOpen()). Never swallow the error and continue using that EntityManager inside long-running queue workers (Messenger / Horizon) — reset it via ManagerRegistry::resetManager().

2. Savepoints (Partial Rollbacks Inside Transactions) & Side-Effect Timing

  • When DB::transaction(...) is nested inside an active outer transaction in Laravel (or via SAVEPOINT in SQL/DBAL), throwing inside the inner block rolls back only to that savepoint, leaving the outer valid statements intact if caught cleanly!
  • Never dispatch emails, webhooks, or queue jobs inside an uncommitted transaction without DB::afterCommit() (or Messenger's dispatch_after_current_bus / transactional outbox): a queue worker can start before the DB transaction commits (seeing missing rows) or execute even if the transaction later rolls back!

Never inject repositories, loggers, or cache services directly into a Doctrine Entity — bind a dedicated Entity Listener cleanly in Symfony/Doctrine:

3. Critical Lifecycle Gotchas (Both ORMs!)

  1. Mass Updates Bypass Hooks!
  • Laravel Post::where('status', 'draft')->update(['status' => 'archived']) and Doctrine DQL UPDATE App\Entity\Post p SET p.status = 'archived' execute direct SQL and DO NOT trigger updating, saved, PreUpdate, or postUpdate hooks!
  1. Never Call $em->flush() Inside a Doctrine prePersist / preUpdate / onFlush Listener!
  • Doing so causes infinite recursion or corrupts the active UnitOfWork commit sequence.
  1. Modifying Properties Inside preUpdate Requires Care / Recompute ChangeSet:
  • In onFlush, changing any entity property requires calling $uow->recomputeSingleEntityChangeSet($classMetadata, $entity) so Doctrine emits SQL for the mutated field.

Key Takeaways

  • Keep external dependencies (Cache, Mailer, Slugger) out of Entities/Models — place side effects in Observers (ShouldHandleEventsAfterCommit) or Doctrine EntityListeners.
  • Remember bulk update() and DQL UPDATE skip every ORM lifecycle callback.

09. Sorting, Offset Traps & Cursor Pagination

Offset pagination (LIMIT 20 OFFSET 200000) feels fine during development with 50 rows, then falls off a performance cliff in production when tables pass millions of rows. Understanding deterministic ordering and keyset/cursor pagination solves both speed and skipped/duplicate rows on infinite feeds.

1. Safe Multi-Column Sorting & Deterministic Tie-Breakers

Always follow two rules on sorted queries:

  1. Strict Sort Allowlist: NEVER pass $request->input('sort') raw into orderBy(). Map user-facing keys (newest, price_asc) through an explicit allowlist array!
  2. Unique Tie-Breaker Column: Sorting non-unique columns (ORDER BY created_at DESC LIMIT 15) lets SQL return ties in nondeterministic order across pages -> always pair a unique trailing tie-breaker (ORDER BY created_at DESC, id DESC).

2. Offset Pagination vs Keyset (Cursor) Pagination

SQL
-- OFFSET Pagination (Page 10,000 -> Scans & discards 249,975 rows EVERY request!)
SELECT id, title, created_at FROM articles ORDER BY id DESC LIMIT 25 OFFSET 249975;

-- CURSOR / KEYSET Pagination (Constant O(log N) B-Tree seek at page 10 or 100,000!)
SELECT id, title, created_at FROM articles WHERE id < 750025 ORDER BY id DESC LIMIT 25;

10. Hydration, Memory Streaming & Caching Tuning

The fastest SQL query still bottlenecks if PHP runs out of RAM hydrating 50,000 full ORM Entities + Identity Map snapshots or misses query/result caches. Master projection, chunked streaming, and caching layers.

1. The Truth About Object Hydration vs Array vs DTO Hydration

Many teams reach for plain associative arrays believing they're universally tiny — let's measure accurately on modern PHP 8.3+:

  • Full Heavy ORM Hydration: populates Model/Entity attributes, $original dirty-check snapshots, Doctrine UnitOfWork Identity Map arrays, bidirectional Collection lazy proxies, and JSON/date cast objects. Costly in CPU and RAM at high row counts!
  • Lightweight Readonly PHP 8.3 DTOs: declared typed properties (final readonly class RowDto { public int $id; ... }) sit in compact fixed property slots and actually consume less RAM per row than PHP associative arrays (HashTable buckets)!
  • Doctrine Scalar / Array Hydration: skips proxy wrapping and Identity Map registration completely (Query::HYDRATE_ARRAY, Query::HYDRATE_SCALAR, Query::HYDRATE_SCALAR_COLUMN) or leaves objects unmanaged ($query->setHint(Query::HINT_READ_ONLY, true)).

Skip Model HydrationDB::table('posts')->select('id', 'title')->get() or ->toBase()$query->getArrayResult() / $query->getScalarResult()

2. Streaming Millions of Rows Without Out-of-Memory (OOM)

NEVER call Model::all() or $repo->findAll() inside cron exports, sitemap generators, or batch migrators! Also disable query logging inside long CLI jobs (DB::disableQueryLog() — Laravel keeps SQL query history arrays in RAM if query logging is enabled in debug mode!).

Eloquent Batch Streaming (chunkById & lazyById)

PHP
DB::disableQueryLog();

// Keyset-based chunks (`WHERE id > last_id LIMIT 500`) — immune to offset drift!
Post::where('status', 'published')->chunkById(500, function ($posts): void {
    foreach ($posts as $post) {
        // Process 500 rows at a time; memory stays flat!
    }
});

// LazyCollection: iterates 1 model at a time cleanly while fetching 500-row pages internally:
foreach (Post::published()->lazyById(500) as $post) {
    // Low constant RAM footprint
}
Pitfall: NEVER use offset-based chunk(500) when mutating the filter column inside the loop (e.g., setting status = 'processed' while querying where('status', 'pending')) — shifted offsets skip every alternate batch! Always use chunkById()!

Doctrine Streaming (toIterable() + Periodic $em->clear())

PHP
$batchSize = 200;
$count = 0;

$iterable = $entityManager->createQuery('SELECT p FROM App\Entity\Post p')
    ->toIterable(); // Streams database cursor rather than loading all rows!

foreach ($iterable as $post) {
    $post->recalculateScore();

    if ((++$count % $batchSize) === 0) {
        $entityManager->flush();
        $entityManager->clear(); // CRITICAL: releases all managed entities from Identity Map RAM!
    }
}
$entityManager->flush();
$entityManager->clear();

3. Caching Tiers (Metadata, Query Plans, Result Sets & SLC)

  1. Doctrine Cache Triad (metadata_cache, query_cache, result_cache):
  • Metadata Cache: parses #[ORM\Entity] attributes ONCE (APCu / Redis) instead of running PHP Reflection per request.
  • Query Cache: caches parsed DQL -> SQL compilation trees.
  • Result Cache: $query->enableResultCache(lifetime: 600, resultCacheId: 'catalog_top_10') for slow read queries (remember explicit invalidation on writes!).
  • Second-Level Cache (SLC): caches immutable/read-mostly Entities (Regions: READ_ONLY / NONSTRICT_READ_WRITE) directly in Redis/APCu across HTTP requests!
  1. Laravel Application & Cache-Aside (remember / flexible):
  • Pair Cache::flexible('catalog.featured', [300, 600], fn () => ...) with PostObserver invalidation (ShouldHandleEventsAfterCommit).

Key Takeaways

  • Always stream large jobs using chunkById() / lazyById() (Eloquent) or $query->toIterable() + periodic $em->clear() (Doctrine), with DB::disableQueryLog().
  • Trim SELECT columns (select(['id', ...])) and hydrate lightweight typed DTOs or scalar arrays on read-heavy endpoints.

Zero-Downtime Expand-and-Contract Column Changes

Never rename or enforce NOT NULL on a hot table with zero transition step while old app code is still serving requests:

  1. Expand: Add the nullable new column (plus composite index online/concurrently).
  2. Dual-Write & Backfill: Deploy code reading fallback and writing both columns; run chunkById backfill in batches.
  3. Contract: Enforce NOT NULL and drop the legacy column in a subsequent deploy.

2. Essential SQL Indexing Rules for ORMs

  • Index EVERY Foreign Key Manually If Needed: MySQL/InnoDB auto-indexes foreign key constraints (foreignId()->constrained()), while PostgreSQL and SQLite DO NOT auto-create indexes on foreign key columns unless you add ->index() explicitly! Missing child indexes turn eager WHERE IN (...) and cascade DELETEs into full table scans!
  • Leftmost-Prefix Composite Indexes: Match your exact WHERE + ORDER BY clauses:
PHP
  // Optimizes: WHERE status = 'active' ORDER BY published_at DESC, id DESC
  $table->index(['status', 'published_at', 'id'], 'idx_posts_status_pub_id');
  • Avoid Low-Selectivity Single Indexes alone on booleans (is_active): combine with tenant/category/timestamp columns ((tenant_id, is_active, created_at)).

3. Seeding, Factories, Fixtures & Testing the Database Boundary

Fast Factories vs Fixtures

  • Laravel Factories: Post::factory(40)->published()->recycle($authors)->sequence([...])->create() reuses parent rows cleanly without spawning 40 extra users!
  • Doctrine Fixtures: ORMExecutor + AbstractFixture classes using addReference('cat_tech', $cat) / getReference(...).

Testing Rules for ORM-Backed Code

  1. Never Mock Eloquent Models or Doctrine Repositories for SQL Queries!

Mocking User::shouldReceive('where') tests your mock setup, not your SQL, casts, foreign keys, triggers, or lockForUpdate queries. Use an actual database via RefreshDatabase (Laravel Pest/PHPUnit) or zenstruck/foundry + DAMA\DoctrineTestBundle (rolls back every test case inside an outer DB transaction in ~2ms!).

  1. Enforce Query Budget Assertions in CI:
PHP
   // Catch N+1 regressions automatically inside Pest / PHPUnit Feature tests!
   DB::flushQueryLog();
   DB::enableQueryLog();

   $this->getJson('/api/v1/posts')->assertOk();

   expect(count(DB::getQueryLog()))->toBeLessThanOrEqual(4);
  1. Engine Parity Matters: SQLite :memory: runs tests fast, but SQLite ignores MySQL/PostgreSQL-specific SQL (strict GROUP BY, FULLTEXT, enum DDL, FOR UPDATE NOWAIT, JSON indexing). Run CI tests against the same PostgreSQL/MySQL engine used in production!

Key Takeaways

  • Index child foreign key columns explicitly when targeting PostgreSQL/SQLite, and align composite index order cleanly with WHERE -> ORDER BY clauses.
  • Inspect every generated migration (--pretend / --dry-run) and test real SQL queries inside transaction-rolled-back integration tests rather than mocking ORM builders.

Knowing how Eloquent and Doctrine work is half the skill — knowing when NOT to wrap Eloquent in a heavy Repository layer, when to bypass ORMs via CQRS Read DTOs, and which ORM fits your project separates maintainable production systems from over-engineered ones.

3. Framework Selection Playbook (Eloquent vs Doctrine)

Choose Laravel Eloquent (Active Record) when:

  • Building SaaS products, CMS platforms, REST APIs, CRUD admin portals, or teams shipping fast with Migrations + Factories + Queues.
  • Domain models map closely 1-to-1 with normalized database tables and business rules live cleanly in Action classes + FormRequests + Policies.

Choose Symfony Doctrine ORM 3 (Data Mapper) when:

  • Building strict Domain-Driven Design (DDD) cores where Domain Entities must remain framework-agnostic POPOs with Value Objects (#[ORM\Embedded]), Inheritance (SINGLE_TABLE/JOINED), and constructor invariants.
  • Managing complex multi-entity object graphs needing an Identity Map ($a === $b), deferred batched flush() commits, or second-level entity caching.

Choose Bypassing the ORM (Raw DBAL / DB::table / CTEs) when:

  • Running BI analytics (WITH RECURSIVE CTEs, window functions ROW_NUMBER() OVER (...), pivot tables).
  • Importing or archiving hundreds of thousands of rows (upsert(), INSERT INTO ... SELECT ...).

4. Production ORM Readiness Checklist & Capstone Blueprint

Build the Multi-Vendor Order & Ledger Engine using every discipline across Chapters 1–12:

  1. Model::shouldBeStrict(! app()->isProduction()) (or Doctrine metadata/query/result APCu/Redis cache in prod).
  2. Money immutable Value Object backed by integer *_cents columns (never FLOAT).
  3. Polymorphic comments/media with Relation::enforceMorphMap() (Eloquent) or Doctrine table inheritance.
  4. DB::transaction(..., attempts: 3) with lockForUpdate() on wallet/inventory stock + version optimistic locks on admin edits + DB::afterCommit() before dispatching notifications.
  5. chunkById(500) / toIterable() + $em->clear() for batch jobs, cursorPaginate(25) on infinite feeds, and automated SQL query-count tests (<= 4 queries) in CI!

// Zero SELECT issued for category row:
$catRef = $em->getReference(Category::class, $categoryId);
$product->assignCategory($catRef);
$em->flush();
Inserting & Saving Records CRUD

Laravel Eloquent uses ActiveRecord where the model itself handles database updates. Symfony Doctrine uses the DataMapper pattern where entities are pure data containers, and the Entity Manager handles database writes.

Laravel (Eloquent ActiveRecord) 
// Instantiate and save directly
$user = new User();
$user->name = 'Jane Doe';
$user->email = 'jane@example.com';
$user->save(); // Writes immediately
Symfony (Doctrine DataMapper) 
// Instantiate, persist in manager unit, flush
$user = new User();
$user->setName('Jane Doe');
$user->setEmail('jane@example.com');

$entityManager->persist($user);
$entityManager->flush(); // Writes to database

Querying active records via Eloquent builder chain versus DQL/repository queries via Doctrine.

Laravel (Eloquent ActiveRecord) 
// Query Builder interface on Model
$users = User::where('status', 'active')
    ->orderBy('name', 'asc')
    ->get();
Symfony (Doctrine DataMapper)

$users = $entityManager->getRepository(User::class)

        ['status' => 'active'],

Mapping models relationships (e.g. Category containing many Products) using PHP methods vs PHP Attributes / Docblock Metadata mappings.

// Defined on Category class model
public function products()
{
    return $this->hasMany(Product::class);
}
Symfony (Doctrine DataMapper)

#[ORM\OneToMany(
    targetEntity: Product::class, 
    mappedBy: 'category'

Eager Loading (N+1 Query Prevention) Relations

Load related associations in a single database query to prevent massive performance degradation (N+1 query execution loops).

Laravel (Eloquent ActiveRecord) 
// Uses the 'with' chain method
$products = Product::with('category')->get();

// Fetch JOIN query inside Repository DQL
$query = $entityManager->createQuery(
    'SELECT p, c FROM App\Entity\Product p 
     INNER JOIN p.category c'
);
$products = $query->getResult();
